# 製品の位置づけと導入判断

## 推奨事項

Boundra はドメイン優先の TypeScript コードベース向けの任意導入型アーキテクチャ契約ツールであり、アプリケーションフレームワークの代替ではありません。中核となる価値は、スキャフォールド作成、import ポリシー、関係の可視化を駆動する共有ドメインマニフェストと、検証済みの入力・結果契約を組み合わせることです。CLI とランタイムは個別に導入できます。

## どのようなチームが導入すべきか

- 複数のビジネスドメインや共有パッケージを持ち、境界の逸脱が繰り返し発生するチーム。
- 複数のエントリーポイントを保守する、または AI 支援によるコード生成を利用しており、明示的でレビュー可能な依存ポリシーを必要とするチーム。
- すでにドメイン優先の構成を求めており、別のフレームワークではなく一貫したスキーマとアダプターを必要とするチーム。

リポジトリの規模だけを理由に導入することは避けてください。小規模なサイトや、すでに Nx またはカスタム ESLint ルールで適切に管理されているアプリケーションでは、得られる効果が小さい場合があります。型付きリモート呼び出しに tRPC を使用しているプロジェクトは、そのまま維持して Boundra の CLI だけを評価できます。

## 代替ツールとの比較

| ツール | 実際の強み | Boundra との比較でのトレードオフ |
| --- | --- | --- |
| ESLint no-restricted-imports | 既存の lint パイプラインで使い慣れた、カスタマイズ可能な静的 import 制限 | チームがパスルールを保守する必要があり、ルール自体はドメインマニフェスト、依存グラフ、契約ジェネレーターを所有しない |
| Nx enforce-module-boundaries | Nx とそのプロジェクトモデルに統合されたプロジェクト・タグベースの制約 | 既存の Nx ワークスペースに適した選択。Boundra のドメインマニフェストとスキーマ契約は、対象がより限定された別のワークフロー |
| dependency-cruiser | 設定可能なモジュール依存ルールとグラフ可視化（到達可能性、循環を含む） | より汎用的なグラフ分析。Boundra の client/server/shared 契約構成は規定しない |
| tRPC | 専用の RPC エコシステムとエンドツーエンドで推論される TypeScript API 型 | RPC が主な課題なら有力な選択。Boundra はソースアーキテクチャを対象とし、トランスポートはホストが所有する |
| Next.js server/client boundaries | ランタイム・フレームワークを認識したコンポーネント構成と環境制約 | Boundra は指定されたソースレイヤーを検査するもので、Next.js のビルド・ランタイムのセマンティクスを代替できない |

一次情報：[ESLint](https://eslint.org/docs/latest/rules/no-restricted-imports)、[Nx](https://nx.dev/docs/kb/enforce-module-boundaries)、[dependency-cruiser](https://github.com/sverweij/dependency-cruiser)、[tRPC](https://trpc.io/docs)、[Next.js](https://nextjs.org/docs/app/getting-started/server-and-client-components)。

これは機能の比較であり、ベンチマーク結果ではありません。代替ツールがカスタム設定を使用して同等のアーキテクチャを表現できないと主張するものでもありません。

## メリットとコスト

| メリット | コストまたは制限 | 根拠 |
| --- | --- | --- |
| 明示的な依存関係の所有権 | マニフェストの更新と公開 API の設計が機能開発の一部になる | BR-004 から BR-006、graph-domains、マニフェスト仕様 |
| 予測可能なファイル配置と生成された契約 | 既存コードの移行が必要な場合がある。生成されたスタブは引き続き実装が必要 | CLI 仕様とクリーンルーム検証 |
| ランタイムスキーマ検証 | 検証とスキーマ作成への依存が増える。認証、永続化、認可は実装しない | 契約とトランスポートの仕様 |
| 機械可読な診断 | 独自パーサー・リゾルバーの対象範囲では未対応の import 解決を見落とす可能性があり、スキャンの合格は完全な分離の証明ではない | パーサーコーパスと設定仕様 |
| ネイティブ CLI | 初回リリースのダウンロードとプラットフォーム対応。オフライン環境ではあらかじめ用意したバイナリが必要 | パッケージング仕様 |

リポジトリの過去の合成ベンチマークの所要時間は [performance.md](performance.md) に記載されています。直接的な比較ではありません。現在の Node 互換性とネイティブターゲットの対応範囲は CI で検証していますが、Next.js および Vite のアプリケーション固有の導入については、引き続き代表的な利用側での検証が必要です。Boundra はセキュリティ境界ではなく、コンパイラー、フレームワーク、デプロイ、アプリケーションのテストに代わるものでもありません。

## エビデンスに基づく次の作業

| 優先度 | 作業 | 合格条件 |
| --- | --- | --- |
| P0 | 信頼できる導入とスキャンのカバレッジ | 新規インストール、想定されるドメインを少なくとも2つスキャン、正常なフィクスチャと実行可能な診断 |
| P1 | 実際の Next.js App Router と Vite の利用側フィクスチャ | コンパイル・ビルド、エイリアス解決、公開エントリー、ランタイムと開発連携を検証 |
| P1 | 参照パーサーおよび確立されたツールとの解析精度比較 | 同一コーパス、厳密な import の組、独立してラベル付けされた結果を使用し、偽陽性・偽陰性を測定 |
| P2 | 導入負荷と性能の評価 | 同一プロジェクト・環境で設定時間、保守手順、繰り返しスキャンの時間とメモリを記録 |

中核部分の導入エビデンスで必要性が示されるまでは、拡張 DSL、新しいルーティングフレームワーク、独自バンドラーを導入しないでください。既存ツールがより低い保守コストで対象のワークフローを満たすなら、独立開発を再検討します。

## 導入の終了基準

パイロットが成功したと言えるのは、開発者が既存ビルドを壊さずに一部を設定でき、チェッカーが意図したドメインを観測でき、診断が実行可能で、繰り返し発生する保守コストが許容できる場合のみです。実際の導入状況や比較速度はまだ測定されていません。評価中は既存の lint、型チェック、フレームワークのビルドを維持してください。
