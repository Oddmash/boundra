# 제품 포지셔닝 및 도입 결정

<a id="recommendation"></a>

## 권장 사항

Boundra는 도메인 중심 TypeScript 코드베이스의 아키텍처 계약을 선택적으로 적용하기 위한 도구이며, 애플리케이션 프레임워크를 대체하지 않습니다. 핵심 가치는 스캐폴딩, import 정책 및 관계 시각화를 이끄는 공통 도메인 매니페스트와 검증된 입력/결과 계약을 결합하는 데 있습니다. CLI와 런타임은 별도로 도입할 수 있습니다.

<a id="who-should-adopt-it"></a>

## 어떤 팀이 도입해야 할까요?

- 여러 비즈니스 도메인과 공유 패키지를 운영하며 경계가 반복적으로 흐트러지는 팀
- 여러 진입점을 유지하거나 AI 지원 코드 생성을 사용하며 명시적이고 리뷰 가능한 의존성 정책이 필요한 팀
- 이미 도메인 중심 구조를 원하며 다른 프레임워크보다 일관된 스키마와 어댑터가 필요한 팀

저장소가 크다는 이유만으로 도입하는 것은 피하세요. 소규모 사이트나 Nx 또는 커스텀 ESLint 규칙으로 이미 성공적으로 관리되는 애플리케이션은 얻는 이점이 적을 수 있습니다. 타입이 지정된 원격 호출을 위해 tRPC를 사용하는 프로젝트는 이를 유지하면서 Boundra CLI만 평가할 수 있습니다.

<a id="alternative-comparison"></a>

## 대안 비교

| 도구 | 실제 장점 | Boundra와 비교한 절충점 |
| --- | --- | --- |
| ESLint no-restricted-imports | 기존 lint 파이프라인에서 익숙하고 사용자 지정 가능한 정적 import 제한 | 팀이 경로 규칙을 유지하며 해당 규칙 자체는 도메인 매니페스트, 의존성 그래프 또는 계약 생성기를 소유하지 않음 |
| Nx enforce-module-boundaries | Nx 및 그 프로젝트 모델과 통합된 프로젝트/태그 기반 제약 | 기존 Nx 워크스페이스에 탁월한 선택이며 Boundra의 도메인 매니페스트 및 스키마 계약은 범위가 더 좁은 다른 워크플로우 |
| dependency-cruiser | 도달 가능성과 순환을 포함한 설정 가능한 모듈 의존성 규칙 및 그래프 시각화 | 보다 일반적인 그래프 분석이며 Boundra의 client/server/shared 계약 구조를 규정하지 않음 |
| tRPC | 전용 RPC 생태계와 추론된 엔드투엔드 TypeScript API 타입 | RPC가 핵심 문제라면 강력한 선택이며 Boundra는 소스 아키텍처를 다루고 전송 계층을 호스트에 맡김 |
| Next.js 서버/클라이언트 경계 | 런타임 및 프레임워크를 인식하는 컴포넌트 합성과 환경 제약 | Boundra는 지정된 소스 계층을 검사하며 Next.js 빌드/런타임 의미를 대체할 수 없음 |

주요 출처: [ESLint](https://eslint.org/docs/latest/rules/no-restricted-imports), [Nx](https://nx.dev/docs/kb/enforce-module-boundaries), [dependency-cruiser](https://github.com/sverweij/dependency-cruiser), [tRPC](https://trpc.io/docs), [Next.js](https://nextjs.org/docs/app/getting-started/server-and-client-components).

이는 기능 비교이며, 벤치마크 결과 또는 대안 도구가 사용자 지정 설정으로 동등한 아키텍처를 표현할 수 없다는 주장이 아닙니다.

<a id="benefits-and-costs"></a>

## 이점과 비용

| 이점 | 비용 또는 제한 | 근거 |
| --- | --- | --- |
| 명시적인 의존성 소유권 | 매니페스트 업데이트 및 공개 API 설계가 기능 개발의 일부가 됨 | BR-004부터 BR-006까지, graph-domains, 매니페스트 명세 |
| 예측 가능한 파일 위치와 생성된 계약 | 기존 코드 마이그레이션이 필요할 수 있고 생성된 스텁은 여전히 구현해야 함 | CLI 명세 및 클린룸 검증 |
| 런타임 스키마 검증 | 검증 작업이 추가되고 스키마 작성에 의존하며 인증, 영속성 또는 인가를 구현하지 않음 | 계약 및 전송 명세 |
| 기계 판독이 가능한 진단 | 커스텀 파서/리졸버 범위에서 지원하지 않는 import 해석이 누락될 수 있으며 검사 통과는 완전한 격리의 증거가 아님 | 파서 코퍼스 및 설정 명세 |
| 네이티브 CLI | 최초 릴리스 다운로드 및 플랫폼 가용성에 제약이 있고 오프라인 환경에서는 바이너리를 미리 준비해야 함 | 패키징 명세 |

저장소의 과거 합성 벤치마크 실행 시간은 [performance.md](performance.md)에 기록되어 있습니다. 이는 도구 간 직접 비교가 아닙니다. 현재의 Node 호환성 및 네이티브 대상 커버리지는 CI에서 검증합니다. Next.js와 Vite 애플리케이션별 도입에는 대표 소비자 검증이 여전히 필요합니다. Boundra는 보안 경계가 아니며 컴파일러, 프레임워크, 배포 또는 애플리케이션 테스트를 대체하지 않습니다.

<a id="evidence-led-next-work"></a>

## 증거 기반 후속 작업

| 우선순위 | 작업 | 통과 기준 |
| --- | --- | --- |
| P0 | 안정적인 도입 및 스캔 범위 | 새로 설치한 후 예상하는 도메인 중 적어도 두 개를 스캔하고, 정상 픽스처와 실행 가능한 진단을 확인 |
| P1 | 실제 Next.js App Router 및 Vite 소비자 픽스처 | 컴파일/빌드 및 별칭 해석, 공개 진입점, 런타임, 개발 통합 검증 |
| P1 | 참조 파서 및 검증된 도구를 기준으로 파서 정밀도 비교 | 동일한 코퍼스, 정확한 import 튜플 및 독립적으로 분류한 결과를 사용하고 거짓 양성 및 거짓 음성을 측정 |
| P2 | 도입 오버헤드와 성능 평가 | 같은 프로젝트와 환경에서 설정 소요 시간, 유지 관리 단계, 반복 스캔 시간 및 메모리를 기록 |

핵심 도입 근거가 필요성을 입증하기 전에는 확장 DSL, 새로운 라우팅 프레임워크 또는 커스텀 번들러를 도입하지 마세요. 기존 도구가 적은 유지 관리로 목표 워크플로우를 충족한다면 독립적인 개발을 재검토하세요.

<a id="adoption-exit-criteria"></a>

## 도입 완료 기준

개발자가 기존 빌드를 깨뜨리지 않고 일부 영역을 설정할 수 있고, 검사기가 의도한 도메인을 관찰하며, 진단에 따라 조치할 수 있고 반복적인 유지 관리 비용이 허용 범위에 있을 때만 시범 도입을 성공으로 판단합니다. 실제 도입과 비교 속도는 아직 측정되지 않았습니다. 평가 중에도 기존 lint, 타입 검사 및 프레임워크 빌드를 유지하세요.
