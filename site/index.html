HOW IT WORKS

Structure you can verify.

Define domains, declare allowed relationships, and check them against your source. The runtime handles schema validation at the application boundary.

01 / ARCHITECTURE

Declare the boundary.

Each domain has layer directories, public entry points and a manifest that specifies its dependencies.

domains/order/
  client/
  server/
  shared/
  domain manifest
02 / STATIC ANALYSIS

Catch drift in CI.

Report forbidden layer imports, undeclared dependencies and internal cross-domain imports.

pnpm exec boundra \
  check-boundaries \
  --format json
03 / CONTRACTS

Validate both directions.

Define input and result schemas, then connect your own transport and API implementation.

defineQuery({
  name: "get-order",
  input: inputSchema,
  result: resultSchema
})

ADOPT INCREMENTALLY

Start with one domain.

Keep your existing framework, build, and backend. Try a single domain before expanding the policy across a repository.

  1. Initializeboundra init --name my-app
  2. Scaffoldboundra create-domain order
  3. Generate a contractboundra generate query order/get-order
  4. Check and visualizeboundra check-boundaries

When Boundra fits

Use it when multiple domains and entry points need consistent dependency policy. A small app or a project already well governed by Nx or ESLint may need little more.

What it is not

Boundra does not replace authorization, a backend framework, a bundler, or runtime integration tests. Static analysis is limited to supported source patterns and configured domains.
